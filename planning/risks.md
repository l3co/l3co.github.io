# Risk assessment — migração de tema

| # | Risco | Categoria | Probabilidade | Impacto | Mitigação |
|---|---|---|---|---|---|
| R1 | Rotas do novo tema não replicam exatamente `/post/<slug>`, `/tags/<tag>`, `/archives`, `/rss.xml`, `/sitemap-index.xml`, quebrando links indexados no Google | migration, compatibility | Medium | High | [phase-02](./phases/phase-02-routing-and-page-parity.md) inclui um passo explícito de diff entre a lista de URLs do `dist/` atual (já buildado, presente no repo) e do `dist/` novo antes do merge. |
| R2 | Pipeline de markdown do tema alvo não suporta callouts (`rehype-callouts`), TOC (`remark-toc`) ou notação de diff/highlight do Shiki usadas em posts técnicos — conteúdo renderiza errado ou sem highlight | migration, compatibility | High | Medium | [phase-03](./phases/phase-03-markdown-pipeline-parity.md) porta a config de markdown inteira antes de tocar em layout visual; validação inclui abrir pelo menos um post com callout e um com diff/highlight. |
| R3 | Dark mode não existe no tema alvo; CSS do tema (`base.css`, `components.css`, `navigation.css`) não foi desenhado com variantes dark — pode exigir retrabalho visual significativo, não só "ligar uma flag" | implementation, architecture | High | Medium | Tratado como fase própria ([phase-04](./phases/phase-04-visual-port-and-dark-mode.md)) em vez de tarefa acoplada a outra; escopo explícito: cobrir header, footer, corpo do post, cards de listagem, busca. Cores extras podem ser aproximadas visualmente, sujeitas a revisão do usuário. |
| R4 | OG image dinâmica (Satori) depende da API experimental `astro:assets` `fontData`/`experimental_getFontFileURL` — comportamento pode mudar entre versões do Astro ou exigir ajuste ao mover para o `astro.config` do tema alvo | dependency, implementation | Low | Medium | Portar `og.png.ts`/`index.png.ts` sem alterações funcionais na Fase 5; validar geração de imagem via build local antes do merge. |
| R5 | Front matter de 90 posts em pt-BR (acentuação, datas, tags) corrompido durante cópia/merge de arquivos entre a estrutura antiga e a nova | data, migration | Low | Critical | Nenhum script de reescrita de dados é necessário (ver [Decision 001](./decisions/decision-001-content-schema-strategy.md)); os arquivos de `src/content/post` são movidos, não regravados. Qualquer script auxiliar deve rodar em modo dry-run com diff revisado antes de aplicar. |
| R6 | Build do GitHub Actions quebra por dependência de CLI externa do Pagefind ou por diferença de versão de `@astrojs/sitemap`/`@astrojs/rss` entre as duas bases | operations, dependency | Low | High | [phase-05](./phases/phase-05-integrations.md) mantém o mesmo comando de build (`astro check && astro build && pagefind --site dist && cp -r dist/pagefind public/`) e revalida o workflow `.github/workflows/astro.yaml` sem alterar seu gatilho (`workflow_dispatch`, seguindo o padrão já usado na migração anterior — ver Q4 em [discovery.md](./discovery.md)). |
| R7 | Merge acidental para `main` antes da revisão visual, publicando um site incompleto em produção | schedule, operations | Low | Critical | Todo o trabalho ocorre em branch nova a partir de `main` ([phase-00](./phases/phase-00-foundation-and-baseline.md)); `astro.yaml` permanece em `workflow_dispatch` manual até aprovação explícita do usuário, como já é o padrão do repositório. |
| R8 | Imagens de posts referenciadas com caminho relativo (`src/content/post/**` ou `public/images/posts`) quebram ao mudar de layout/base de assets | migration, compatibility | Medium | Medium | [phase-01](./phases/phase-01-content-schema-and-migration.md) inclui varredura de todos os caminhos de imagem usados no front matter (`ogImage`) e no corpo dos posts antes de portar os componentes visuais. |

## Ações irreversíveis identificadas

- Merge da branch de migração em `main` (dispara possibilidade de deploy). Mitigado por R7: mantido manual até aprovação.
- Nenhuma exclusão de dado de produção é necessária neste plano — os arquivos atuais (`src/content/post`, `src/content/pages`) são preservados; o que é substituído é a camada de apresentação (layouts/componentes/estilos) e config de build.

## Rollback

Como todo o trabalho ocorre em branch isolada (fora de `main`), o rollback é trivial: não mergear / reverter o merge commit. Não há migração de dado em produção (banco, CMS externo) associada a este plano.
